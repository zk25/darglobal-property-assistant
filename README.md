# Property Assistant: DarGlobal & Wasalt

Live demo: https://darglobal-property-assistant-8wnc.onrender.com (free hosting, so the first load can take about a minute)

A retrieval-augmented chatbot that answers questions about DarGlobal's developments and Wasalt's property services using data scraped from their public websites. Answers are generated by a free model on OpenRouter, streamed to the browser, and cite the pages they came from. The app runs in a single Docker container and is deployed on Render.

Technical assignment for the Junior AI Engineer (Applied AI) role at DarGlobal.

## Features

- App-style layout on desktop and mobile: a floating navigation rail (bottom bar on phones), a market picker, and three views: **Assistant** (chat), **Explore** (map with picture pins, country filters, search and project cards) and **Saved** (favourites kept in the browser)
- Project detail sheet with key facts, highlights and one-tap questions that open the chat
- Answers that name a project show its card, so the user can go from chat to details in one tap
- Grounded answers with numbered citations that link to the source page
- Streaming responses
- Follow-up questions ("when will it be ready?") and English or Arabic input
- Buyer-style wording is understood: "2 bhk flat" is matched to "2-bedroom apartment", "ceo" to "chief executive"
- Says when something isn't published (most prices) and gives the right sales contact instead of guessing
- Keeps answering when free models are rate-limited: model fallback, automatic discovery of current free models, then an answer built directly from the retrieved facts

Example questions: *Which DarGlobal projects are in Dubai?* · *Tell me about Trump Tower Jeddah* · *What residency do I get if I buy in Oman?* · *How do Wasalt property auctions work?* · *Are there 2 bhk flats in Dubai?*

## Architecture

```
Browser ── POST /api/chat/stream ──► FastAPI
                                       │
                 1. query rewriting    │  "2 bhk flats" → "2 bedroom apartment"; Arabic → English search query
                 2. retrieval          │  hybrid TF-IDF over heading-level chunks (word 1-2 grams + char 3-5 grams)
                                       │  + heading boost; follow-ups reuse the previous question
                 3. prompt             │  system rules + 6 numbered notes + last 6 turns
                 4. generation         │  OpenRouter free model, streamed (SSE); fallback chain before first token
                 5. post-processing    │  strip <think> blocks, renumber citations to match the source list
                                       ▼
                  event: delta … event: done {answer, sources, follow_ups}
```

| Component | File |
|---|---|
| API, prompt, citations, fallback answers, rate limit, cache | `app/main.py` |
| Chunking, query rewriting, hybrid retrieval | `app/rag.py` |
| OpenRouter client: streaming, fallback, free-model discovery | `app/llm.py` |
| Front end (vanilla JS, no build step) | `app/static/index.html`, `app.css`, `app.js` |
| Map (Leaflet, bundled; OpenStreetMap tiles) | `app/static/vendor/` |
| Crawler for both sites | `scraper/scrape.py` |
| Knowledge base (Markdown with source URLs) | `data/` |
| Structured project data for cards and map | `data/projects.json` |
| Retrieval and API tests | `tests/test_app.py` |

### Design decisions

**Lexical retrieval instead of embeddings.** The curated corpus is about 90 chunks (about 445 when the scraped pages are included). TF-IDF with character n-grams is accurate at this size, tolerant of typos and brand names, deterministic, and starts in under a second on a free CPU container with no model download. The upgrade path for a larger corpus is multilingual embeddings (e.g. BGE-M3) in FAISS with a cross-encoder re-ranker; the `KnowledgeBase.search` interface would stay the same.

**Section-level chunks with their own source.** Documents are split at headings, so a chunk is one coherent topic (a project, a residency programme). Sections that come from a different page carry a `Source:` line, so every citation opens the exact page.

**Grounding.** The model sees only numbered notes and is told to cite them, never invent prices, dates or availability, and treat note text as data rather than instructions (prompt-injection guard).

**Built for free-tier limits.** Free models are rate-limited and change often. The client tries configured models in order, switches only before the first streamed token, discovers currently free models from `/models` when all fail, remembers the last working model, and caches repeated questions. An answer that stops part-way is marked as cut off and is not cached. If no model responds, the answer is assembled from the most relevant lines of the retrieved sections.

**Chat and browsing in one place.** Buyers often start by looking, not asking. The Explore view lets them browse by country on a map; every project sheet offers questions that hand off to the assistant, and assistant answers that name a project link back to its card. Project cards use generated illustrations rather than photos, so nothing implies an image shows the real building; map pins mark approximate locations.

**Security.** The API key comes only from an environment secret. Inputs are length-limited, and requests are rate-limited per visitor and across all visitors. The UI escapes all HTML before rendering its small Markdown subset.

## Evaluation

`tests/` contains 67 checks, including:

- top-1 retrieval for the suggested questions, top-3 retrieval for 17 more
- buyer wording ("2 bhk flats") and follow-up handling
- citation renumbering, streaming and fallback behaviour, `<think>` filtering across chunk boundaries
- input validation and source URLs for every document
- cut-off streams, provider error formats, greetings, rate limits and answers about a named project (`tests/test_fixes.py`)

```bash
pytest -q
```

## Data

`data/darglobal/` and `data/wasalt/` contain the cleaned knowledge base: content from about 30 public pages (DarGlobal home, about, projects, investor, why-invest, hospitality, golf, membership, tokenization, project pages and 2026 press releases; Wasalt home, corporate and about pages and blog, plus press coverage of Wasalt). Each file lists its source URLs.

`scraper/scrape.py` crawls both sites politely (robots.txt, delay between requests, same domain, English pages only) and writes one Markdown file per page to `data/scraped/`, which the app loads together with the curated files unless `INCLUDE_SCRAPED=0`. The curated files alone give more accurate answers, so the demo is meant to run with `INCLUDE_SCRAPED=0`. Pages that render their text with JavaScript return too little text and are listed as skipped in `data/scraped/manifest.json`.

```bash
python scraper/scrape.py --max-pages 40
```

Snapshot: November 2026. Most prices and payment plans are not published on the sites.

## Deploy on Render

1. Create a **Web Service** from this repository. Render builds the `Dockerfile`.
2. Under **Environment**, add `OPENROUTER_API_KEY`. The `Dockerfile` already sets `INCLUDE_SCRAPED=0`.
3. After the deploy, open `/api/health` to check that `llm_enabled` is true. Then ask a question; if the model does not answer, the reason is in the logs after `LLM unavailable`.

## Pipeline

Keys live in `.env` (copied from `.env.example`). It is git-ignored, Docker-ignored and never uploaded.

```bash
bash scripts/pipeline.sh      # venv + dependencies → scrape both sites → tests → live model check → Docker build (if Docker is running)
bash scripts/run_local.sh     # run the app at http://127.0.0.1:7860
python scripts/deploy_hf.py   # create/update the Hugging Face Space, set the key as a secret, wait until live
```

| Step | What it does |
|---|---|
| `pipeline.sh` 1–2 | Creates `.venv`, installs `requirements-dev.txt`, loads `.env` and checks the OpenRouter key |
| `pipeline.sh` 3 | Crawls darglobal.co.uk and wasalt.sa into `data/scraped/` (the app loads these with the curated files) |
| `pipeline.sh` 4 | Runs the test suite against the curated knowledge base |
| `pipeline.sh` 5 | Starts the server and asks a real question; fails with the server's reason if the model doesn't answer |
| `pipeline.sh` 6 | Builds the Docker image if Docker is available |
| `deploy_hf.py` | Creates the Space (Docker SDK), uploads the code and data, stores `OPENROUTER_API_KEY` as a private Space secret, restarts, waits for `RUNNING` and checks `/api/health` |

Manual alternatives:

```bash
docker build -t property-assistant . && docker run -p 7860:7860 --env-file .env property-assistant
```

Or create a Docker Space on huggingface.co, upload the files (not `.env`), add the `OPENROUTER_API_KEY` secret under **Settings → Variables and secrets**, and restart the Space.

## Configuration

| Variable | Default | Purpose |
|---|---|---|
| `OPENROUTER_API_KEY` | none | OpenRouter key (secret) |
| `OPENROUTER_MODELS` | three free models | Comma-separated models, tried in order |
| `OPENROUTER_BASE_URL` | `https://openrouter.ai/api/v1` | API base (useful for testing) |
| `APP_URL` | empty | Sent to OpenRouter as the referer |
| `RATE_LIMIT_PER_MIN` | `15` | Messages per minute per visitor |
| `GLOBAL_LIMIT_PER_MIN` | `60` | Messages per minute for all visitors together |
| `PORT` | `7860` | Server port |
| `INCLUDE_SCRAPED` | `1` (the `Dockerfile` sets `0`) | Load `data/scraped/` pages into the knowledge base |
| `HF_TOKEN`, `HF_SPACE` | none | Used only by `scripts/deploy_hf.py` |

## Limitations and next steps

- Data is a snapshot; a scheduled re-scrape (e.g. a nightly GitHub Action) would keep it current.
- Retrieval is lexical; embeddings and re-ranking would help with heavily paraphrased questions.
- Free models have daily request caps; a paid fallback model would make the demo fully reliable.
- An evaluation set of real buyer questions with graded answers would allow tuning beyond retrieval accuracy.
